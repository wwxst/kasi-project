# 媒体账号绑定与通用报备设计规格

日期：2026-08-17

## 1. 文档定位

本文只设计“推广用户媒体账号绑定”和“媒体账号向短剧平台报备”模块，作为多短剧平台推广业务的一个独立实施单元。

本文描述的业务行为已完成后端实现并通过自动化验证，等待用户验收。当前仓库通过 `V2__media_account_filing.sql` 和 `V4__media_filing_task_version.sql` 建立平台接入、媒体账号、平台报备和资料版本隔离结构；媒体账号 API、GoodShort 报备提交/查询任务、三态状态、任务重试、管理员编辑和绑定用户删除保护均已实现。管理后台媒体账号报备页面已接入查询、详情、编辑和失败重试；推广用户端页面仍未接入。

本模块依赖平台接入基础模块提供：短剧平台、平台接入账号、加密凭据、能力声明、统一平台适配器注册和 GoodShort 签名/HTTP 基础设施。媒体账号模块不直接读取 `pid` 或密钥。

## 2. 本模块目标

- 一个推广用户可以绑定多个媒体账号。
- 同一个真实媒体账号只能绑定一个推广用户，且不允许转让。
- 同一个媒体账号可以分别向多个短剧平台报备，各平台状态互不影响。
- 用户可查看本人媒体账号及各平台报备状态，并对失败报备手动重试。
- 管理员可分页查询全部媒体账号、查看报备情况并代用户重新提交。
- 报备业务状态统一为“审核中、已加白、已失败”。
- GoodShort 首期通过统一报备接口接入，不把 GoodShort 特有字段扩散到媒体账号业务层。
- 平台暂时不可用时可自动重试，多实例执行时不会重复并发处理同一条报备。
- 用户改错资料后，旧异步结果不能覆盖新资料对应的报备状态。
- 绑定过媒体账号的推广用户不能物理删除，只能禁用，以保留永久归属和历史归因。

## 3. 明确不在本模块实现

- 短剧目录同步、短剧上下架和免费内容。
- 分佣比例配置与预计佣金计算。
- 推广链接、口令、素材下载和活动归因。
- 订单同步、退款、结算订单导出和转化分析。
- 媒体账号转让、合并或跨用户迁移。
- 自动证明某个账号确实归提交用户所有。首期以平台报备审核结果作为外部确认。
- GoodShort 未提供的 TikTok 锚点能力。
- 同一平台多套启用机构账号的前端选择和自动分流；数据仍按 `connection_id` 隔离。

## 4. 方案选择

### 4.1 采用：媒体账号主表加平台报备表

通用媒体账号保存在 `promotion_media_account`，每次向某个平台接入账号报备的状态保存在 `provider_media_filing`。两者是一对多关系。

该方案允许一个 TikTok 账号同时在 GoodShort 和未来平台 B 报备，GoodShort 审核失败不会影响平台 B 的状态。媒体账号归属、启停和资料只维护一次，平台报备状态分别维护。

### 4.2 不采用：把 GoodShort 报备字段直接放入媒体账号表

该方案首期字段较少，但一个账号只能保存一套平台状态。接入第二个平台时必须拆表并迁移线上数据，也容易把 GoodShort 的状态码和接口字段泄漏到通用业务层。

### 4.3 不采用：每个平台建立独立媒体账号表

该方案会重复账号归属、唯一性、启停、权限和查询逻辑，且无法可靠阻止同一个媒体账号被不同用户通过不同平台重复绑定。

## 5. 核心业务关系

```text
推广用户 promotion_user
  └─ 媒体账号 promotion_media_account
       ├─ GoodShort 报备 provider_media_filing
       ├─ 平台 B 报备 provider_media_filing
       └─ 平台 C 报备 provider_media_filing
```

平台报备记录实际绑定平台接入账号：

```text
媒体账号
  + 平台接入账号 connection_id
  = 唯一一条平台报备记录
```

推广用户不查看或选择机构 `pid`。用户只选择短剧平台，系统选择该平台当前启用的接入账号；首期每个平台只有一套启用账号。

## 6. 媒体账号模型

### 6.1 字段

`promotion_media_account` 规划字段：

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | `BIGINT` | 内部自增主键 |
| `user_id` | `BIGINT` | 所属推广用户内部 ID，创建后不可修改 |
| `media_type` | `VARCHAR(32)` | 媒体平台统一编码 |
| `external_account_id` | `VARCHAR(128)` | 媒体平台账号 ID |
| `account_name` | `VARCHAR(128)` | 账号名称，可空 |
| `account_link` | `VARCHAR(512)` | 主页链接，可空 |
| `status` | `TINYINT` | `1` 启用，`0` 停用 |
| `data_version` | `INT` | 资料版本，从 1 开始，资料变更时递增 |
| `created_at` | `DATETIME` | 创建时间 |
| `updated_at` | `DATETIME` | 更新时间 |

不设置 `deleted_at`，也不提供物理删除媒体账号的接口。停用账号仍保留全部报备记录，并供后续链接、订单和统计模块建立历史关联。

### 6.2 媒体平台编码

首期统一编码为：

- `TIKTOK`
- `FACEBOOK`
- `YOUTUBE`
- `INSTAGRAM`

GoodShort 只接受以上四种媒体平台。未来增加媒体类型时，需要同时确认目标短剧平台的映射能力；不能把未知字符串直接透传第三方。

### 6.3 唯一性与输入规范

- 数据库唯一约束为 `(media_type, external_account_id)`。
- `media_type` 转为大写枚举保存。
- `external_account_id` 去除首尾空白后保存，不允许空值。
- 唯一索引使用数据库统一的大小写不敏感字符排序规则，阻止仅大小写不同的重复账号。
- `account_name` 去除首尾空白，空字符串转为 `NULL`。
- `account_link` 去除首尾空白，空字符串转为 `NULL`；非空时必须是合法的 `https` URL。

该唯一性阻止相同“媒体平台 + 账号 ID”被重复绑定。首期不根据主页链接、昵称或第三方页面自动推断两个不同 ID 是否属于同一真实账号。

### 6.4 归属与修改规则

- `user_id` 永远不能修改，不提供账号转让。
- 账号处于审核中或已失败，且所有平台均未加白时，用户可以修改媒体平台、账号 ID、名称和主页链接。
- 任一平台已经加白后，媒体平台和账号 ID 永久锁定；更换账号必须新增另一条媒体账号。
- 已加白后仍可修改账号名称和主页链接，系统将新资料重新同步到已存在的各平台报备；身份字段未变化时，本地已加白状态不因资料同步暂时降级。
- 修改媒体平台或账号 ID 时，再次执行全局唯一性检查。
- 每次资料修改递增 `data_version`，报备任务必须携带并校验对应版本。

### 6.5 启用与停用

- 新建媒体账号默认启用。
- 用户可以停用和重新启用本人账号。
- 停用后不能新建平台报备、重试失败报备或生成新的推广链接。
- 已存在报备记录和已加白状态继续保留；后台仍可低频复核已加白状态。
- 重新启用不自动创建新的平台报备，用户可继续使用原报备状态或主动重试失败记录。

## 7. 推广用户删除规则

媒体账号要求永久归属，后续订单和统计也需要稳定引用原推广用户。因此本模块实施后修改现有推广用户删除规则：

- 从未绑定过媒体账号的推广用户仍可物理删除，手机号和邮箱可复用。
- 只要存在一条归属该用户的 `promotion_media_account`，该推广用户就不允许物理删除，只能禁用。
- 管理接口收到这类删除请求时返回明确业务错误，不自动改成禁用，避免操作语义不透明。
- 数据库通过 `promotion_media_account.user_id -> promotion_user.id` 外键和 `ON DELETE RESTRICT` 做最终保护；Service 在执行删除前先检查并返回稳定业务错误。
- 媒体账号不能物理删除，因此“曾绑定过”与“当前存在媒体账号记录”含义一致。

## 8. 平台报备模型

### 8.1 字段

`provider_media_filing` 规划字段：

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `id` | `BIGINT` | 内部自增主键 |
| `connection_id` | `BIGINT` | 平台接入账号 ID |
| `media_account_id` | `BIGINT` | 媒体账号 ID |
| `status` | `VARCHAR(16)` | `PENDING`、`APPROVED`、`FAILED` |
| `submitted_data_version` | `INT` | 最近成功提交给平台的账号资料版本，可空 |
| `remote_status` | `VARCHAR(64)` | 第三方原始状态，供管理员排查，可空 |
| `external_filing_id` | `VARCHAR(128)` | 第三方报备 ID，平台提供时保存，可空 |
| `filing_time` | `DATETIME` | 第三方报备时间，可空 |
| `operate_time` | `DATETIME` | 第三方审核时间，可空 |
| `next_action` | `VARCHAR(16)` | 内部任务动作 `SUBMIT`、`QUERY` 或 `NONE` |
| `next_action_at` | `DATETIME` | 下次执行时间，可空 |
| `retry_count` | `INT` | 当前动作连续失败次数 |
| `last_submitted_at` | `DATETIME` | 最近成功提交时间，可空 |
| `last_queried_at` | `DATETIME` | 最近成功查询时间，可空 |
| `last_error_code` | `VARCHAR(64)` | 脱敏后的最近错误类型，可空 |
| `last_error_message` | `VARCHAR(512)` | 脱敏后的管理员排障信息，可空 |
| `lease_owner` | `VARCHAR(64)` | 多实例任务租约持有者，可空 |
| `lease_until` | `DATETIME` | 租约到期时间，可空 |
| `created_at` | `DATETIME` | 创建时间 |
| `updated_at` | `DATETIME` | 更新时间 |

唯一约束为 `(connection_id, media_account_id)`。外键均使用 `ON DELETE RESTRICT`，报备记录不物理删除。

`next_action`、重试次数和租约属于内部执行状态，不新增面向用户的第四种报备状态。

### 8.2 业务状态

| 状态 | 中文 | 含义 |
|---|---|---|
| `PENDING` | 审核中 | 已进入提交或查询流程，尚未得到最终通过结果 |
| `APPROVED` | 已加白 | 平台明确返回审核通过 |
| `FAILED` | 已失败 | 平台明确拒绝/失效，或待审核流程达到配置的连续重试上限 |

只有 `APPROVED` 才能在对应 `connection_id` 下生成新推广链接。

### 8.3 状态流转

```text
首次提交或用户重试
  -> PENDING + SUBMIT

提交成功
  -> PENDING + QUERY

查询返回审核中
  -> PENDING + QUERY

查询返回已加白
  -> APPROVED + QUERY（转为低频复核）

查询返回拒绝或失效
  -> FAILED + NONE

待审核阶段连续技术失败达到上限
  -> FAILED + NONE

FAILED 手动重试
  -> PENDING + SUBMIT
```

平台超时、限流、5xx 或临时网络错误不会在第一次发生时直接把业务状态改成已失败。任务按指数退避重试；首期默认退避为 1、5、15、30、60 分钟，之后每 60 分钟一次，连续 10 次仍不能完成待审核动作时转为 `FAILED`。次数和间隔必须可配置。

已经 `APPROVED` 的记录只因平台明确返回失败/失效而转为 `FAILED`；低频复核的网络错误保留 `APPROVED`，避免因平台短暂故障错误撤销用户资格。

### 8.4 资料版本与旧结果隔离

异步提交和查询开始前读取媒体账号当前 `data_version`。任务写回结果时必须再次校验版本：

- 任务版本等于当前版本，才允许更新当前报备状态。
- 任务执行期间用户修改了资料，旧任务结果直接丢弃，不覆盖新版本。
- 身份字段被修改时，所有已有报备记录回到 `PENDING + SUBMIT`。
- 仅名称或主页链接变化时，未加白记录回到 `PENDING + SUBMIT`；已加白记录保留 `APPROVED`，同时设置 `SUBMIT` 同步新资料。

该规则防止“旧账号 ID 的查询结果”把“用户刚改正的新账号 ID”错误标为已加白。

## 9. 用户操作流程

### 9.1 绑定并报备

1. 用户选择媒体平台，填写账号 ID，可填写账号名称和主页链接，并选择要报备的短剧平台。
2. 后端从认证上下文取得当前推广用户内部 ID，不接受前端指定 `userId`。
3. 校验推广用户和平台均启用，平台存在启用接入账号并声明账号报备能力。
4. 在同一数据库事务内创建媒体账号和对应 `PENDING` 报备记录。
5. 事务提交后由任务执行器尽快向第三方提交；接口不等待第三方审核。
6. 用户页面立即显示“审核中”，之后通过查询接口刷新状态。

若媒体账号创建成功但本地报备记录创建失败，整个事务回滚。第三方调用不放在数据库事务内，避免网络等待长期占用事务和数据库连接。

### 9.2 向另一个平台报备

用户在已有媒体账号下选择另一个平台。系统校验该平台存在启用接入账号和报备能力，然后创建另一条独立报备记录。原平台状态不改变。

### 9.3 修改填错资料

- 所有平台均未加白时，允许修正媒体平台和账号 ID；系统对已有报备重新提交。
- 任一平台已加白后，媒体平台和账号 ID 不可修改，接口返回“已加白账号身份不可修改”。
- 名称和主页链接可修改，并按资料版本规则同步。

### 9.4 重试失败报备

用户或管理员可以对 `FAILED` 记录发起重试。重试只重置该平台报备为 `PENDING + SUBMIT`，不会影响同一媒体账号在其他平台的状态。

对 `PENDING` 重复点击重试返回幂等成功，不创建第二条报备；对 `APPROVED` 点击重试不执行操作并返回明确业务错误。

## 10. 通用平台报备接口

平台适配层按能力拆分接口，避免把账号报备塞进一个包含全部短剧、订单和分析方法的超大接口。

```java
public interface AccountFilingProviderAdapter {
    String providerCode();

    void submitAccountFiling(
            ProviderConnectionSecret connection,
            AccountFilingSubmission submission);

    AccountFilingResult queryAccountFiling(
            ProviderConnectionSecret connection,
            AccountFilingQuery query);
}
```

通用请求只包含：媒体平台、账号 ID、账号名称和主页链接。通用查询结果包含：统一状态、第三方原始状态、第三方报备 ID、报备时间和操作时间。

适配器必须将错误归类为：

- 临时错误：超时、限流、连接失败、5xx，可重试。
- 第三方业务拒绝：参数不支持、账号明确拒绝或失效，可转换为 `FAILED`。
- 本地配置错误：接入账号停用、凭据不可用或平台不支持报备，不发起远程请求并交由管理员处理。

平台密钥、签名前原文、完整第三方响应和内部 URL 不进入用户响应。日志和 `last_error_message` 必须脱敏。

## 11. GoodShort 适配

### 11.1 报备提交

调用：

```text
POST /open/filing/report
```

字段映射：

| 本地字段 | GoodShort 字段 |
|---|---|
| 机构接入账号 | `pid` |
| 服务端当前毫秒时间 | `timestamp` |
| 固定报备类型 | `type=ACCOUNT` |
| `media_type` | `media` |
| `external_account_id` | `accountId` |
| `account_name` | `accountName`，空值不发送 |
| `account_link` | `accountLink`，空值不发送 |

签名使用平台接入基础模块统一实现，并通过 `sign` 请求头发送。返回必须同时满足 `status == 0` 和 `success == true` 才视为提交成功。

GoodShort 未提供客户端幂等键。重试时复用相同的 `pid + media + accountId + type`，不生成新的本地报备记录；根据该接口的账号报备语义，将相同账号的重复提交视为更新/重报操作。正式联调时必须验证重复提交行为和限流规则。

### 11.2 报备查询

调用：

```text
POST /open/filing/query
```

请求使用 `pid`、`timestamp`、`type=ACCOUNT`、`media` 和 `accountId`。状态映射：

| GoodShort `status` | 本地状态 |
|---|---|
| `0` | `PENDING` |
| `1` | `APPROVED` |
| `2` | `FAILED` |

保存 GoodShort 返回的 `filingTime` 和 `operateTime`。未知状态不猜测为审核通过，保持当前安全状态并记录管理员可见异常；待审核记录继续重试，已加白记录保持已加白直到平台返回明确状态。

### 11.3 查询频率

- 提交成功后 1 分钟首次查询。
- `PENDING` 默认每 5 分钟查询一次。
- `APPROVED` 默认每天复核一次，用于发现平台明确返回的失效或拒绝。
- 所有频率和重试上限通过配置提供，不能硬编码在 Controller。
- GoodShort 文档限流为 100 次/分钟；任务调度必须按接入账号限速并预留其他接口额度。

## 12. 异步执行与并发

### 12.1 数据库记录作为持久任务

本模块不额外引入消息队列。`provider_media_filing.next_action` 和 `next_action_at` 组成持久任务来源，应用重启后仍能继续处理。

定时执行器按到期时间扫描任务。多实例通过 `lease_owner + lease_until` 原子领取记录；租约到期后其他实例可以接管。单次批量数、并发数和平台限速均由配置控制。

### 12.2 幂等与并发约束

- `(connection_id, media_account_id)` 唯一索引防止重复创建报备。
- 创建或重试遇到唯一键冲突后重新读取现有记录，返回同一业务对象。
- 同一报备同一时刻只允许一个有效租约。
- 状态更新同时校验记录 ID、资料版本和租约持有者。
- 用户修改资料与任务写回冲突时，以新资料版本为准，旧任务结果不生效。

## 13. API 设计

所有响应继续使用 `ApiResponse<T>`；请求使用 `*DTO`，响应使用 `*VO`。

### 13.1 推广用户接口

统一位于 `/api/user/promotion/media-accounts`，要求 `ROLE_USER`：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/user/promotion/media-accounts` | 查询本人全部媒体账号及各平台报备摘要 |
| `GET` | `/api/user/promotion/media-accounts/{id}` | 查询本人单个账号详情 |
| `POST` | `/api/user/promotion/media-accounts` | 创建媒体账号，并向请求中的一个平台发起报备 |
| `PUT` | `/api/user/promotion/media-accounts/{id}` | 修改本人媒体账号资料 |
| `PATCH` | `/api/user/promotion/media-accounts/{id}/status` | 启用或停用本人媒体账号 |
| `POST` | `/api/user/promotion/media-accounts/{id}/filings/{providerId}` | 向另一平台首次报备，或重试该平台失败报备 |

创建请求中的平台为单个 `providerId`。以后用户需要向多个平台报备时逐个平台调用报备接口，避免一次请求包含多次第三方操作和部分成功语义。

所有详情、修改、启停和报备操作都必须同时按 `id + 当前认证 user_id` 查询；查询不到统一返回资源不存在，不能泄漏其他用户是否拥有该账号。

### 13.2 管理员接口

统一位于 `/api/admin/promotion/media-accounts`，要求 `ROLE_ADMIN`：

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/api/admin/promotion/media-accounts` | 分页查询全部账号，可按用户编号、媒体平台、启停状态、短剧平台和报备状态筛选 |
| `GET` | `/api/admin/promotion/media-accounts/{id}` | 查看账号、所属用户和全部平台报备详情 |
| `POST` | `/api/admin/promotion/media-accounts/{id}/filings/{providerId}/retry` | 代用户重试失败报备 |

首期管理员不修改媒体账号归属或身份字段，也不删除媒体账号。管理员重试前同样校验账号启用、平台启用、接入账号可用和平台能力。

### 13.3 响应边界

用户媒体账号响应包含：账号 ID、媒体平台、外部账号 ID、账号名称、主页链接、启停状态、各平台名称与三态报备结果、第三方报备/操作时间和最近同步时间。

管理员响应可额外包含：推广用户 `userNo`、昵称/姓名、接入账号名称、原始第三方状态、重试次数和脱敏错误信息。

任何响应均不包含平台 `pid`、密钥、密文、签名原文、任务租约持有者或推广用户内部 `user_id`。

## 14. 权限与安全

- 用户只能操作本人媒体账号，归属只从 JWT 认证上下文取得。
- 管理员只能查看和重试，不能借管理接口转移账号归属。
- 第三方账号 ID 和主页链接按普通个人资料处理，不写入无必要的业务日志。
- 平台凭据只由平台接入服务解密后以短生命周期对象传给适配器，不保存在报备表。
- 第三方响应中的未知字段不整体序列化入库，避免保存无关个人信息或敏感数据。
- 用户停用或管理员禁用推广用户后，不允许创建、修改或重试媒体账号；后台仍可维护已有报备状态。

## 15. 错误处理

实施时只增加实际可达的错误枚举，至少覆盖以下业务情形：

- 媒体账号不存在或不属于当前用户。
- 同一媒体平台账号已被其他推广用户绑定。
- 已加白账号的媒体平台或账号 ID 不可修改。
- 媒体账号已停用。
- 推广用户已禁用。
- 平台不存在、已停用或没有启用接入账号。
- 平台不支持媒体账号报备或不支持该媒体类型。
- 报备已加白，不允许重复重试。
- 绑定过媒体账号的推广用户不允许物理删除。
- 第三方暂时不可用。

用户接口不透传 GoodShort 的原始错误文本。临时错误通常由后台自动重试，创建和重试接口只要本地任务已可靠落库即可返回“审核中”。

## 16. 事务边界

- 创建媒体账号和首次报备记录在同一事务完成。
- 修改账号资料和重置相关报备任务在同一事务完成。
- 手动重试只更新一条报备记录，在单个事务完成。
- 第三方 HTTP 调用不放入以上数据库事务。
- 任务写回单次只更新当前报备记录，使用资料版本和租约条件防止错误覆盖。
- 修改现有推广用户删除服务时，Service 先检查媒体账号，再进入现有会话失效和物理删除流程；数据库外键负责处理极端并发下的最终冲突。

## 17. 测试设计

### 17.1 迁移与持久化

- 生产迁移在隔离 H2 MySQL 模式数据库实际执行。
- 媒体账号全局唯一约束和平台报备唯一约束生效。
- 外键阻止删除已绑定媒体账号的推广用户。
- Mapper 每个只操作一张主表。

### 17.2 媒体账号业务

- 一个用户绑定多个不同媒体账号成功。
- 同一媒体账号不能被另一个用户绑定。
- 同一账号大小写不同或带首尾空白时仍被识别为重复。
- 所有平台未加白时可修改填错的媒体类型和账号 ID。
- 任一平台已加白后不能修改媒体类型和账号 ID。
- 已加白后修改名称或主页链接会创建新版本并安排同步，但保持已加白状态。
- 用户不能读取、修改、停用或报备他人账号。
- 停用账号不能新增或重试报备，重新启用后可继续操作。

### 17.3 平台报备业务

- 同一账号可在两个平台分别报备且状态独立。
- GoodShort `0/1/2` 准确映射为 `PENDING/APPROVED/FAILED`。
- GoodShort 请求字段、签名头、空选填字段和时间字段映射正确。
- 平台不支持的媒体类型在远程调用前被拒绝。
- `PENDING` 技术失败按配置退避，达到上限后进入 `FAILED`。
- `APPROVED` 复核遇到网络失败时保持已加白，明确返回失败时才转为已失败。
- 失败记录可手动重试，已加白记录不能重复重试。
- 修改资料后，旧版本任务结果不能覆盖新版本状态。
- 多实例同时扫描时只有一个任务实例获得租约。

### 17.4 权限与现有用户管理回归

- 匿名请求返回 401，错误角色返回 403。
- USER 只能访问本人媒体账号接口。
- ADMIN 可查看全部账号并重试，但不能通过接口修改归属或删除账号。
- 从未绑定媒体账号的推广用户仍可物理删除。
- 绑定过媒体账号的推广用户删除返回稳定业务错误，禁用仍成功。
- 响应和日志测试确认不包含 `pid`、平台密钥或密文。
- 新增控制器测试继承 `BaseAuthTest`，并覆盖正常路径和权限越界。

## 18. 可观测性

- 任务日志记录平台编码、接入账号内部 ID、报备内部 ID、动作、耗时和结果，不记录平台密钥和完整用户资料。
- 管理员可查看最近提交/查询时间、连续失败次数、下次执行时间和脱敏错误。
- 指标至少包含提交成功/失败数、查询成功/失败数、各报备状态数量、任务积压数和租约超时回收数。
- 用户页面显示最近同步时间，避免把轮询状态描述为实时审核结果。

## 19. 验收标准

本模块只有同时满足以下条件才可描述为已实现：

- 用户可以绑定多个媒体账号，重复账号无法归属给不同用户。
- 同一账号可以向多个平台建立独立报备。
- GoodShort 报备提交和查询通过适配器完成，三种状态映射正确。
- 用户和管理员权限边界通过自动化测试。
- 修改资料时旧任务结果不会污染新版本。
- 异步任务可重试、可在重启后继续，并能避免多实例并发重复处理。
- 绑定过媒体账号的推广用户无法物理删除，但仍可禁用。
- 完整测试套件在 Java 25 下零失败、零错误，`git diff --check` 无问题。
- README、AGENTS.md 和模块路线图只在代码真正实现后更新为当前行为。
