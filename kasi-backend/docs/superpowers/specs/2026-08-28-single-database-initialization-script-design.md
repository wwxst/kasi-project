# 单一数据库初始化脚本设计

## 目标

项目尚未进入生产且开发数据库无须保留历史数据。移除 Flyway 版本迁移机制，只保留一份可在空 MySQL 数据库上执行的完整初始化 SQL。

## 当前问题

当前最终数据库结构分散在 `V1`、`V13` 至 `V20` 的 SQL/Java 迁移中。新环境必须按版本顺序执行，且 `V17`、`V18` 包含仅为历史库兼容而存在的修补逻辑。对于可以直接删除重建的开发库，这些历史迁移不再有价值。

## 方案

- 唯一生产初始化文件为 `src/main/resources/db/kasi_promotion.sql`。
- 初始化文件直接声明当前最终表结构、索引、默认值和必要种子数据；表间 `*_id` 仅作为逻辑关联，由应用层校验，不使用物理外键或数据库级联。
- 不保留面向旧库的 `ALTER TABLE`、历史数据回填或兼容分支。
- 删除 `db/migration` 下的 Flyway SQL、`db.migration` Java 迁移类、Flyway Maven 依赖和运行配置。
- 应用启动不再自动创建或升级数据库；部署前由运维或开发人员对空库手动执行初始化 SQL。
- H2 测试仍使用 `src/test/resources/test-schema.sql`。验证生产初始化结构的测试直接执行 `classpath:db/kasi_promotion.sql`，不再调用 Flyway。

## 数据保留与重建

不提供历史数据迁移和回滚脚本。现有开发数据库由用户自行删除；回滚应用代码时也必须使用与旧代码匹配的空库重新初始化。

## 非目标

- 不修改业务表字段语义、Java API 或运行时业务逻辑。
- 不连接、删除或重建当前开发数据库。
- 不删除 Flyway 之外的本地开发 seed 脚本。

## 验收

- 仓库中不再存在 Flyway 依赖、配置或迁移类。
- `src/main/resources/db` 下只有一份生产初始化 SQL。
- 初始化 SQL 在隔离的 H2 MySQL 模式数据库中可从空库完整执行。
- 受影响的数据库结构测试、编译和 `git diff --check` 通过。
