# 架构决策记录规范

本文件定义本仓库如何记录重要架构决策。重要决策不能只存在于聊天、代码注释或某次提交信息中。

## 1. 何时必须记录

满足任一条件就必须新增或更新记录：

- 改变模块边界、依赖方向、事务边界或数据所有权；
- 改变 API、DTO、错误码、权限、会话、配置或数据库契约；
- 引入或移除外部平台、异步任务、缓存、一致性或并发模型；
- 采用破坏性重构、迁移/重建策略或影响运行与发布流程的技术方案；
- 明确拒绝一个会影响后续实现的备选方案。

单纯修复单模块内部实现且不改变上述契约时，可在模块文档和提交说明中记录，不必新增 ADR。

## 2. 记录位置与状态

本文件是索引和规则入口；详细记录可直接追加在本文件，或放在 `docs/adr/ADR-XXXX-<slug>.md` 并在此处建立索引。状态只能使用：

- `提议`：正在讨论，不能作为当前实现依据；
- `已批准`：方案已确认，但尚未全部交付；
- `已实施`：代码、数据库结构、测试和文档已完成并有验证证据；
- `已废弃`：被新决策替代，必须链接替代记录。

README 和 AGENTS 只能引用 `已实施` 的当前行为；`提议`、`已批准` 和 `已废弃` 必须明确标注状态。

## 3. 必填记录格式

```markdown
# ADR-XXXX: 标题

- 日期：YYYY-MM-DD
- 状态：提议 | 已批准 | 已实施 | 已废弃
- 范围：模块、接口、数据表或运行环境
- 关联：任务、Issue、设计文档、替代或被替代 ADR

## 背景与问题
描述触发决策的事实、约束和根因证据。

## 决策
写出唯一明确的采用方案、边界和不做的事情。

## 备选方案
列出至少一个被拒绝方案及拒绝理由；没有实际备选时说明原因。

## 影响
说明对 API、数据、权限、性能、运维、测试和开发体验的正负影响。

## 迁移与回滚
说明开发库重建、数据库初始化、数据迁移、发布顺序和失败回滚方式；不需要时写明“不需要”。

## 验证证据
列出测试命令、关键结果、运行环境和文档同步位置。
```

## ADR-0001：GoodShort 订单自动同步复用通用定时任务

- 日期：2026-08-25
- 状态：已实施
- 范围：`promotion`、`scheduledtask`、`system_scheduled_task`、管理端定时任务页
- 关联：`docs/superpowers/specs/2026-08-25-goodshort-order-scheduled-sync-design.md`、`src/main/resources/db/kasi_promotion.sql`

### 背景与问题

GoodShort 订单原先只能由管理员手动调用同步接口，无法稳定形成订单归因和 CPS 佣金数据。仓库已有每分钟扫描 `system_scheduled_task`、数据库租约和定时任务管理页；订单分页、幂等、归因和佣金快照也已有实现。

### 决策

新增固定任务 `GOODSHORT_ORDER_SYNC`，默认每分钟同步最近 3 天。复用现有调度扫描器、任务租约和管理页，不增加第二个 Spring `@Scheduled`、第二张任务表或第二个页面。抽取 `PromotionOrderSyncService`，供自动任务和 `POST /api/admin/promotion/orders/sync` 手动补拉共同使用。自动窗口由调度器的 `Clock` 计算为 `now.minusDays(3)` 到 `now`；历史范围继续由管理员显式传入。

任务有效周期由 `cycle_type=INTERVAL_MINUTES` 和 `interval_value=1` 驱动；当前 schema 不保留旧版 `interval_minutes` 兼容字段。

### 备选方案

拒绝新增第二个 Spring `@Scheduled`：会形成重复的周期配置、并发控制和运维入口。拒绝在调度器中复制订单分页代码：会使手动和自动同步的归因、汇总和异常语义分叉。

### 影响

初始化 SQL 植入任务记录，应用提供订单同步 Service；已有订单表、手动 API、订单归因、幂等、五项费率快照和退款冲销语义不变。自动任务失败仍沿用现有调度器日志和下一轮调度行为；本次不新增运行历史、死信、检查点或告警。

### 迁移与回滚

空库执行 `src/main/resources/db/kasi_promotion.sql` 时植入 `GOODSHORT_ORDER_SYNC`。回滚时先在任务页禁用该任务，再回退应用版本；已同步订单保留，不删除订单数据。

### 验证证据

Java 25 下后端完整测试共 364 个通过，0 失败、0 错误、1 个既有跳过；管理端定时任务 API/页面测试共 14 个通过，生产构建成功。

## ADR-0002：使用单一 SQL 手动初始化空数据库

- 日期：2026-08-28
- 状态：已实施
- 范围：数据库初始化、应用启动、构建依赖、数据库结构测试
- 关联：`docs/superpowers/specs/2026-08-28-single-database-initialization-script-design.md`、`src/main/resources/db/kasi_promotion.sql`

### 背景与问题

项目仍处于开发阶段，现有开发数据库没有需要保留的历史数据，之后会直接删除。数据库最终结构分散在多个 SQL 和 Java 版本迁移中，包含只为旧开发库升级服务的补列、回填和默认值修补逻辑。

### 决策

删除 Flyway 依赖、配置和全部版本迁移。只保留 `src/main/resources/db/kasi_promotion.sql`，由开发或部署人员在应用首次启动前对空 schema 手动执行。该文件直接定义当前全部表、索引、默认值和固定初始数据；所有 `*_id` 仅作为逻辑关联，由 Service 校验存在性与归属，不使用物理外键或数据库级联；应用启动不创建、升级或修补数据库。

### 备选方案

拒绝保留一个 Flyway `V1`：虽然也能从空库创建结构，但仍会让应用拥有自动迁移职责，与本次明确要求不符。拒绝继续维护增量版本：当前没有历史数据需要兼容，保留补丁迁移只会增加重建路径复杂度。

### 影响

部署前必须显式创建空 schema 并执行初始化 SQL。结构变更直接更新唯一 SQL，并同步 H2 测试 schema（包括查询索引名称与列顺序）；数据库结构测试在隔离的 H2 MySQL 模式数据库中直接执行生产初始化 SQL。业务 API、字段语义和运行时业务逻辑不变。

### 迁移与回滚

不迁移历史数据。本次不连接或删除现有开发数据库；由用户手动删除后创建空库并执行初始化 SQL。回滚到旧应用版本时也必须使用与旧版本匹配的空库重新初始化，不能在现有 schema 上执行降级。

### 验证证据

Java 25 下数据库初始化与结构聚焦测试通过；完整 Maven 测试 364 个，0 失败、0 错误、1 个既有跳过；`test-compile` 成功。
