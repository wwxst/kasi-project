# 仓库文档与开发规范

本文件是 Kasi monorepo 的统一工程规范。根目录文档描述跨项目规则；`kasi-backend/`、`kasi-admin-web/` 和 `kasi-user-web/` 的 README 只描述项目特有的技术、命令和边界。

## 文档分层

- `AGENTS.md`：代理和开发者必须遵守的强制边界与安全规则。
- `DEVELOPMENT.md`：日常开发、验证和发布流程入口。
- `docs/architecture/`：当前已经实现的系统边界和领域关系。
- `docs/adr/`：重要架构决策及其状态；编号连续，不删除历史记录。
- `docs/development/`：工程规范、测试、Git 发布和当前缺口。
- `docs/projects/`：各子项目现状、运行方式和独立技术边界。
- `docs/plans/`：已批准但尚未全部实施的计划。
- `docs/archive/`：历史设计和已完成计划，仅供追溯，不能作为当前行为契约。

根目录文档是跨项目规范的唯一真相源。子项目若需要补充规则，应在子项目 README 中说明，并链接回根目录；不得复制一份可能过期的根级规则。

## 当前、计划与历史

每份文档必须明确内容属于以下哪一种状态：

- **当前已实现**：代码、迁移、测试和运行行为已经验证。
- **已批准未实施**：方案已确认，但不能描述为现有能力。
- **建议或缺口**：尚未确认或尚未排期的事项。
- **历史归档**：曾经的方案或实现，仅用于追溯。

业务文档不得把计划中的项目管理、CPA、CPM、CapCut、钱包或自动结算写成当前功能。当前快速上线主线是 GoodShort 短剧 CPS；短剧已有分佣和订单逻辑优先复用。

## 变更流程

1. 修改前在仓库根目录执行 `git status --short --branch`，确认任务边界和已有改动。
2. 对缺陷记录现象、影响、复现步骤、证据、根因假设和排除项；先定位根因，再做最小改动。
3. 跨项目 API、数据库、权限、事务、调度或配置契约变更，先写 ADR 或计划并明确迁移、回滚和验证方式。
4. 先补充针对性测试，再修改实现；不要用大范围重构替代具体问题修复。
5. 代码、迁移、接口或运行行为变化时，同步更新根级文档和对应项目文档。
6. 完成后分别运行受影响项目的测试、类型检查、lint、构建和 `git diff --check`。

禁止使用 `git reset --hard`、`git checkout --` 或未经明确批准的 force push。不得覆盖或丢弃用户已有的工作区改动。

## 代码与数据约束

- Controller 只处理 HTTP 协议和参数校验；Service 负责业务编排和事务；Mapper 负责单表持久化。
- Service 接口与 `impl` 分离；请求使用 DTO，响应使用 VO；DTO 使用 Jakarta Validation。
- 多表写操作的事务边界定义在 Service 层；外部 HTTP 调用不得放在数据库事务内。
- 数据库结构只通过 Flyway 新增版本迁移管理，已执行迁移不得静默修改或覆盖。
- 原始上游数据、归因字段、价格/费率快照和最终结算结果分开保存；历史账单不能被新价格改写。
- 不按项目名称写死业务分支；结算类型和明确规则才是业务驱动依据。
- 不提交密码、令牌、API 密钥、真实生产账号、`.env`、日志、`node_modules`、`target` 或 `dist`。

## 测试与发布证据

测试必须使用仓库提供的测试环境：后端使用 Java 25、H2 和 test profile，前端使用锁文件安装的 pnpm 依赖。发布前记录：

- 后端 Maven 测试和编译结果；
- 两个前端的测试、类型检查、lint、格式检查和生产构建结果；
- Flyway 迁移顺序及数据库备份/回滚路径；
- 本地 HEAD、跟踪分支和远端分支哈希一致性。

详细命令见 [DEVELOPMENT.md](../../DEVELOPMENT.md)，Git 发布规则见 [git-and-release.md](git-and-release.md)，当前缺口见 [gaps.md](gaps.md)。
