# GoodShort 短剧目录每日全量同步设计

## 状态

本方案已于 2026-09-12 经用户确认并完成实施；持久层、目录服务、固定任务和管理端聚焦测试已通过，完整 Gate 结果记录在实施计划中。

## 背景

当前系统已经支持管理员手动触发 GoodShort 短剧目录全量同步，也支持固定周期的目录增量同步。甲方在目录响应中明确返回非在线状态时，现有 upsert 会把我方已上架短剧改为本地下架；甲方重新返回在线状态时，远端状态会恢复在线，但不会自动恢复我方上架状态。

当前缺口是：甲方直接删除短剧、导致该短剧不再出现在全量目录响应中时，现有同步只保存本次返回的数据，不会处理历史记录。该历史短剧可能继续保持“远端在线、本地已上架”，并继续出现在用户端。

## 目标

- 新增固定任务 `GOODSHORT_DRAMA_FULL_SYNC`，默认每天 `03:00` 触发 GoodShort 短剧目录全量同步。
- 每次任务覆盖 `DramaSyncProperties.languages` 当前配置的全部语言；默认配置为 13 种语言。
- 单个连接、单个语言的全量分页全部成功后，将本轮未返回的历史短剧标记为“全量未返回”并本地下架。
- 甲方以后重新返回该短剧时，恢复展示真实远端状态和最近可见时间，但不自动恢复本地上架。
- 复用现有 `remote_show_status`、`local_status` 和 `last_seen_at`，不新增数据库字段。

## 非目标

- 不物理删除短剧、剧集、推广元数据或历史同步记录。
- 不新增独立的远端删除时间、重新上架时间或状态历史表。
- 不自动恢复本地上架，不替管理员作出重新发布决定。
- 不改变增量同步周期、免费剧集同步策略或用户端可见条件。
- 不增加新的调度器、Runner、Manager 或并行同步框架。

## 方案比较

### 方案一：仅把缺失短剧本地下架

全量成功后只将 `local_status` 改为 `OFFLINE`，保留原 `remote_show_status`。

优点是后端改动最少。缺点是甲方已经不再返回该短剧时，管理端仍可能显示旧的“远端在线”，无法区分“当前未返回”和“此前最后一次返回时在线”，也无法直观看出后续重新出现。

### 方案二：复用远端状态字段记录“全量未返回”（采用）

全量成功后，将缺失短剧的 `remote_show_status` 改为本地哨兵值 `MISSING`，同时将 `local_status` 改为 `OFFLINE`。管理端把 `MISSING` 展示为“全量未返回”，而不是“已下架”。

甲方重新返回该短剧时，现有 upsert 使用甲方真实 `showStatus` 覆盖 `MISSING`，并刷新 `last_seen_at`；由于本地状态已经是 `OFFLINE`，仍保持本地下架。管理员可以看到“远端在线、本地已下架”，再决定是否手动上架。

该方案不增加 schema，能表达当前目录可见性，并保留管理员人工发布边界。`MISSING` 是我方根据一次完整全量结果推导出的状态，不宣称它是甲方接口原始值。

### 方案三：新增缺失时间或远端状态历史

新增 `remote_missing_at`、重新出现时间或状态事件表，可以提供完整审计历史，但会扩大 schema、API、查询和页面范围。当前需求只要求安全下架和识别重新出现，因此不采用。

## 调度设计

### 固定任务

- 任务编码：`GOODSHORT_DRAMA_FULL_SYNC`
- 标题：`GoodShort 短剧目录全量同步`
- 周期：`DAILY`
- 执行时间：`03:00:00`
- 默认状态：启用
- 业务时区：沿用系统唯一时区 `Asia/Shanghai`
- 任务说明：`每天 03:00 同步 GoodShort 全量短剧目录`

通过新的不可变 Flyway 迁移插入固定任务，同时更新开发空库重建脚本和测试固定任务数据。现有 `V10__localize_goodshort_analytical_report_task.sql` 不修改，新迁移使用下一个可用版本。

### 调度执行

调度分发器查找 `GOODSHORT` 平台后，调用新的目录服务入口 `requestScheduledFull(providerId, configuredLanguages)`。该入口复用现有 checkpoint、展示运行记录和目录 worker：

- 展示运行记录使用 `FULL / SCHEDULED`。
- 每种语言创建或重置一个 `FULL` checkpoint，从第 1 页开始形成新的完整快照。
- 同一连接、同一语言已有 `REQUESTED` 或 `RUNNING` 的全量/增量任务时，本次跳过该语言，不并发执行。
- 其他没有冲突的语言继续入队，不因一个语言冲突而阻止全部语言。
- 入队后由现有目录 worker、租约和兜底扫描机制处理，不新增执行线程模型。

## 全量对账设计

### 快照边界

每个语言的 `FULL` checkpoint 使用本轮稳定的 `requested_at` 作为快照起点。每条甲方实际返回的短剧继续在 upsert 时把 `last_seen_at` 更新为当前时间。

失败任务续跑时不得改变原快照起点，否则前面已经成功处理的页面会被误判为本轮未返回。checkpoint 的重新请求规则调整为：

- 新一轮全量同步：重置页码、计数和 `requested_at`。
- 同一轮失败续跑：保留页码、计数和原 `requested_at`。
- 每日定时任务遇到非运行中的旧 checkpoint 时，始终开始一轮新的全量同步，而不是继承上一天的失败快照。

### 缺失判定

仅在某个连接、某个语言的全量响应处理到 `hasNext=false` 后执行。缺失范围必须同时满足：

- `connection_id` 等于本次同步连接；
- `language` 等于本次同步语言；
- `last_seen_at IS NULL`，或 `last_seen_at < 本轮 requested_at`。

对命中的记录执行：

- `remote_show_status = 'MISSING'`；
- `local_status = 'OFFLINE'`；
- 更新本地 `updated_at`；
- 保留 `last_seen_at`，用于显示最后一次在甲方目录中看到它的时间；
- 保留 `remote_updated_at`、短剧资料、剧集和推广元数据。

已是 `MISSING / OFFLINE` 的记录不重复写入。甲方明确返回非在线状态的短剧仍保存甲方真实状态，不改成 `MISSING`。

### 成功原子性

缺失记录批量下架和 checkpoint 成功收口必须位于同一个本地数据库事务中。事务先通过带 `checkpoint id + lease_owner + RUNNING` 条件的成功更新确认当前 worker 仍持有租约，再执行缺失记录更新，最后一起提交。

如果租约已丢失、批量更新失败或事务提交失败，本轮不得留下“部分缺失短剧已下架但 checkpoint 未成功”的状态；按现有失败处理记录任务失败。全量分页尚未完成或任意页面失败时，不执行缺失对账。

## 重新出现与展示

当后续全量或增量响应再次返回曾经 `MISSING` 的短剧时：

- `remote_show_status` 更新为甲方本次真实状态；
- `last_seen_at` 更新为本次看到的时间；
- `local_status` 继续保持 `OFFLINE`；
- 管理员看到“远端在线、本地已下架”后，可使用现有操作手动上架。

管理端目录列表和详情复用现有“远端状态”“本地状态”“最近同步可见”字段，只补充 `MISSING -> 全量未返回` 的标签映射。详情中的状态值说明应区分甲方原始状态与我方推导的 `MISSING`，避免把哨兵值描述成甲方原始返回值。

用户端查询继续要求 `local_status='PUBLISHED' AND remote_show_status='1'`，因此甲方明确下架或全量未返回的短剧都不可见；重新出现后仍需管理员手动上架才重新对用户可见。

## 失败与边界

- 找不到 GoodShort 平台、接入未启用或能力不可用时，不调用真实接口，也不执行缺失对账。
- 单语言失败只影响该语言；其他完整成功的语言可以独立完成对账。
- 返回页对象或记录集合为 `null` 时沿用现有失败规则，不把它当成空目录。
- 甲方明确成功返回空目录且 `hasNext=false` 时，该语言历史记录均属于本轮未返回并下架；不额外猜测甲方数据量下限。
- 定时全量与现有全量、增量继续遵守同连接/语言互斥，不放宽租约和 checkpoint 约束。
- 定时任务只负责创建目录同步任务；远端处理结果继续由目录同步记录展示，不把“成功入队”伪装成“远端同步成功”。

## 数据库与兼容性

本方案不修改 `provider_drama` 表结构。数据库变更仅新增一条 `system_scheduled_task` 固定任务数据，因此：

- 生产通过新的 Flyway 迁移发布；不修改已经存在的迁移。
- 开发空库重建脚本包含相同固定任务。
- `BaseAuthTest` 的固定任务 fixture 增加相同任务；初始化脚本测试验证开发重建数据，迁移契约测试验证新增 Flyway 数据。
- 管理端定时任务 API 继续使用现有枚举和通用编辑接口，无需新增 Controller API。

## 验证设计

实施时先增加失败测试，再完成最小实现。

### 持久层

- 全量成功后，只把同连接、同语言且本轮未见的记录更新为 `MISSING / OFFLINE`。
- 本轮已见、其他语言、其他连接的记录不变。
- 已经 `MISSING / OFFLINE` 的记录不重复更新。
- 重新 upsert 在线记录后，远端状态恢复 `1`、最近可见时间刷新、本地仍是 `OFFLINE`。

### 目录同步服务

- 每日全量入口按配置语言创建 `FULL / SCHEDULED` 任务并从第一页开始。
- 某语言已有活动任务时只跳过该语言。
- 所有页面成功后，在成功收口事务中执行缺失对账。
- 页面失败、远端拒绝、瞬时异常、租约丢失时不执行缺失对账。
- 失败续跑保留同一快照起点，新的每日全量使用新的快照起点。

### 固定任务

- 迁移和开发重建脚本均存在 `GOODSHORT_DRAMA_FULL_SYNC`，周期为 `DAILY`、时间为 `03:00:00`、默认启用。
- 调度分发器将该任务派发到 `requestScheduledFull`，使用配置中的全部语言。
- 找不到 GoodShort 平台时不调用目录服务。
- 定时任务管理接口返回中文标题和默认配置。

### 管理端

- `remoteShowStatus='MISSING'` 时，列表和详情显示“全量未返回”。
- `1` 仍显示“在线”，甲方其他非在线值仍显示“已下架”。
- “远端在线、本地已下架”继续保持两个独立标签，不新增自动上架操作。

### Gate

- 后端相关聚焦测试 RED/GREEN。
- 管理端相关聚焦测试 RED/GREEN。
- 使用命令局部 JDK 25，在 `kasi-backend` 目录运行 `.\mvnw.cmd verify`。
- 运行 `kasi-admin-web` 的 `pnpm check`。
- 根目录运行 `git diff --check`。
- 未配置真实 MySQL 或 GoodShort 凭据时分别记录 `SKIP`，不得写为 `PASS`。

## 验收标准

- 系统定时任务页面能看到并编辑“GoodShort 短剧目录全量同步”，默认每天 03:00 启用。
- 到期后为 GoodShort 配置语言创建 `FULL / SCHEDULED` 目录同步记录。
- 只有完整成功的语言执行缺失对账，失败或未完成语言不会批量下架。
- 甲方本轮未返回的短剧显示“全量未返回、本地已下架”，用户端不可见，数据未被物理删除。
- 甲方重新返回后显示真实远端状态，本地仍已下架，管理员可明确判断并手动决定是否重新上架。
