# 媒体账号报白批量状态操作设计

## 目标

在管理端 `/promotion/media-accounts` 表格增加行复选框和“批量通过”“批量未通过”操作，让管理员可以批量更新当前页人工报白记录的状态。

## 范围

- 只修改 `kasi-admin-web`，复用现有单条人工状态接口。
- 仅 `filingMethod=MANUAL` 且存在 `providerId` 的行可选；API 报白及没有报白平台的行禁用复选框。
- 选择范围限当前页；翻页、重新查询或改变筛选条件后清空选择。
- 保留现有单条“报白通过”“报白未通过”和其他账号报备操作。
- 不新增后端批量 API，不修改 schema、权限或状态流转规则。

## 交互

表格开启受控行选择。工具栏在导出按钮前增加“批量通过”和“批量未通过”，没有选择记录时两个按钮均禁用。

点击批量按钮后显示确认弹窗和本次将要更新的记录数量。已经处于目标状态的选中记录不发请求；如果所有选中记录都已经是目标状态，则不打开无意义的请求批次，并提示无需更新。

确认后，对需要更新的记录并发调用现有单条状态接口。操作期间两个批量按钮进入禁用状态，避免重复提交。

## 结果处理

- 全部成功：提示成功数量，清空选择并刷新列表。
- 部分失败：提示成功和失败数量，刷新列表，仅保留失败记录的选择，便于管理员重试。
- 全部失败：提示失败数量，刷新列表并保留失败记录的选择。
- 认证失效继续使用现有统一处理，不重复显示页面错误。

单条请求仍由后端完成状态合法性和并发校验。批量操作不承诺事务原子性，每条记录独立成功或失败。

## 测试

页面测试覆盖：

- 人工报白行可选，API 报白和无平台行不可选。
- 未选择时批量按钮禁用。
- 批量通过和批量未通过使用选中行的账号 ID、平台 ID 和目标状态调用现有接口。
- 已处于目标状态的记录被跳过。
- 成功后清空选择并刷新。
- 部分失败后提示统计并只保留失败记录。
- 翻页或重新查询后清空选择。

API 客户端和后端接口未变，不新增对应契约测试。完成前运行管理端聚焦测试、`pnpm check` 和根目录 `git diff --check`。
