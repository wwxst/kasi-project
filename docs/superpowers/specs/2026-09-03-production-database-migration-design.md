# 生产数据库增量迁移设计

状态：已实施；生产目标环境执行仍需发布审批和备份证据。

日期：2026-09-03

## 1. 背景与目标

当前项目使用 `kasi-backend/src/main/resources/db/kasi_promotion.sql` 对空库进行一次性初始化，仓库尚未接入生产增量迁移机制。项目上线后数据库不能再通过删库重建方式升级，因此需要建立可审计、可验证、可停止的生产迁移流程。

本设计采用 Flyway 管理版本化 SQL。迁移作为独立发布步骤执行，应用启动不自动修改数据库。

## 2. 已确认决策

- 迁移工具：Flyway。
- 迁移执行方式：独立发布步骤，不在应用启动时自动执行。
- 生产迁移脚本目录：`kasi-backend/src/main/resources/db/migration/`。
- 当前完整结构冻结为 `V1__baseline.sql`。
- 后续变更只能新增 `V2__...sql`、`V3__...sql` 等脚本，不修改已执行脚本。
- 原 `kasi_promotion.sql` 保留为开发环境空库重建脚本，不作为生产升级入口。
- 每次新增迁移时同步更新 `kasi_promotion.sql` 的最终结构，并通过自动化结构对比防止两者漂移。
- 迁移脚本不得写入数据库密码、JWT 密钥、平台密钥或其他凭据。

## 3. 基线策略

### 3.1 新空库

新建空库后由 Flyway 执行 `V1__baseline.sql`，再按版本顺序执行后续迁移。

### 3.2 已按旧脚本初始化的数据库

已经使用 `kasi_promotion.sql` 建好的数据库，不重新建表。首次接入 Flyway 时执行一次版本为 `1` 的 baseline，使 Flyway 将当前数据库登记为 `V1`；之后只执行新增版本。

禁止打开 `baselineOnMigrate` 作为长期兜底，避免错误数据库被静默登记为基线。baseline 必须由发布人员确认数据库结构后显式执行。

## 4. 执行与配置

实现阶段在 Maven 中加入固定版本的 Flyway 插件和独立 `migration` profile。生产数据库 URL、用户名和密码只从发布环境变量或发布平台密钥注入。

应用运行时关闭 Flyway 自动迁移。迁移 profile 使用以下安全约束：

- `validateOnMigrate=true`。
- `outOfOrder=false`。
- `cleanDisabled=true`。
- 不提供生产数据库连接默认值。
- 使用 Flyway 默认数据库锁，禁止多个发布任务并发迁移。

预期命令：

```powershell
.\mvnw.cmd -Pmigration flyway:info
.\mvnw.cmd -Pmigration flyway:validate
.\mvnw.cmd -Pmigration flyway:migrate
```

实际参数名和凭据注入方式在实施计划中固定，并确保命令不会把密码打印到日志。

## 5. 发布顺序

1. 冻结待发布代码和迁移文件。
2. 备份生产数据库，并确认备份可恢复。
3. 执行 `flyway info`，核对待执行版本。
4. 执行 `flyway validate`。
5. 执行 `flyway migrate`。
6. 检查迁移结果和应用健康接口。
7. 发布与迁移兼容的应用版本。
8. 观察登录、验证码、推广链接、订单同步和定时任务等关键路径。

迁移失败时立即停止发布，不跳过版本，不手工修改 `flyway_schema_history`。根据失败点选择恢复备份或新增修复迁移。

## 6. 事务、回滚与兼容性

MySQL 部分 DDL 会隐式提交，不能假设一组 DDL 可以整体自动回滚。因此迁移应保持单一目的、粒度小、可重试，并在执行前完成备份。

数据库变更采用 expand-contract：

1. 先增加新字段或新表，保持旧应用可运行。
2. 发布能同时识别旧结构和新结构的兼容代码，并完成必要数据回填。
3. 数据核对通过后，在后续迁移中增加非空约束或删除旧字段。

不为每个迁移强制生成反向脚本。破坏性变更通过备份恢复或新的正向修复迁移处理。

## 7. 验证要求

每个迁移至少验证以下场景：

- MySQL 8.4 空库从 `V1` 执行到最新版本。
- 已有 `V1` 结构的数据库升级到最新版本。
- 分别用最新 `kasi_promotion.sql` 和完整 Flyway 迁移链创建空库，比较表、列、索引、约束及固定初始数据，确认最终状态一致。
- `flyway validate` 对版本顺序、命名和校验和正常工作。
- 后端完整 `mvnw verify` 通过。
- MySQL Contract 通过关键索引、精度、时区、锁和事务检查。
- 应用启动、健康接口和关键业务冒烟通过。
- 迁移失败时发布流程停止，未跳过版本。

MySQL 8.0.44 可作为本地兼容性验证环境；项目正式 Contract 基线仍为 MySQL 8.4。

## 8. 文件与职责边界

- `kasi_promotion.sql`：开发环境空库重建便利脚本，描述最新最终结构，不负责生产升级。
- `db/migration/V*.sql`：生产结构和数据迁移的唯一版本真相。
- MySQL 结构对比 Gate：保证开发初始化脚本的最终结果与完整迁移链一致。
- Maven `migration` profile：提供可重复的迁移命令，不改变应用启动行为。
- 发布平台：注入数据库凭据、执行备份和迁移、保存迁移日志。
- 应用：启动时只连接并使用已完成迁移的数据库。

## 9. 非目标

- 本设计不实现正式账单、钱包、提现或其他业务功能。
- 本设计不引入应用启动自动迁移。
- 本设计不保留历史 Flyway 脚本作为当前生产状态，也不把生产密钥写入迁移文件。

## 10. 生产执行前置条件

仓库内 Flyway profile、`V1`、结构一致性 Contract、CI 和发布文档已经实现。实际连接生产数据库前仍需要确认：

- 首次生产部署是否已经执行旧初始化 SQL。
- 生产发布平台如何安全注入 Flyway 连接参数。
- 备份、恢复和迁移日志的保存位置。
- MySQL 8.4 Contract 在目标环境可执行。

在这些条件确认前，不得对生产数据库执行 baseline 或 migrate。应用启动迁移保持关闭，开发数据库仍可从完整重建 SQL 创建。
