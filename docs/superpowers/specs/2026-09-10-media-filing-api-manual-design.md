# GoodShort 按媒体选择报白方式与统一状态方案

日期：2026-09-10

状态：业务方向、五个状态（待提交、审核中、已加白、未通过、提交失败）、新建人工报白直接进入审核中、提交失败时用户端显示审核中、管理端所有状态账号均可删除、全部表格导出统一使用 `.xlsx`、账号报白导出的 11 列名称与顺序、人工/API 双向切换规则、批量提交调度、任务版本单调递增及提交结果不确定时的人工核实流程均已确认；本文为待实施设计。首次上线的生产存量范围仍需发布前核对，下文明确标注的其他实施建议尚待确认。

## 1. 已确认的业务范围

根据本次沟通，GoodShort 的 Facebook 账号继续使用 API 报白，其他媒体账号由运营人工同步给甲方。系统在 GoodShort API 接入配置中提供媒体复选框：勾选使用 API 报白，未勾选使用人工报白。

系统还需支持已有记录在人工报白与 API 报白之间双向切换。已确认采用第 8 节的状态接续规则，替代此前“配置只影响新记录”的建议：终态不重报，人工审核中转 API 先查询，人工待提交转 API 进入后台提交队列，API 转人工停止后续 API 动作并由运营接续处理。

管理端按条删除：选中哪条媒体账号，就只删除该账号及其关联报白记录，不影响其他账号。不再按该账号的报白方式、报白状态或任务是否执行限制删除，待提交、审核中、已加白、未通过、提交失败均适用。不新增一键清空或批量删除功能；用户端不新增删除入口。

人工报白与 API 报白共用以下五个完整报白状态，管理端列表、详情、筛选和导出使用同一含义；用户端对提交失败有下述单独展示规则：

| 业务状态 | API 报白 | 人工报白 |
| --- | --- | --- |
| 待提交 | 尚未提交或正在提交，尚无本次提交失败结果 | 仅用于方式切换后保留的存量状态，新建人工记录不进入此状态 |
| 审核中 | 提交接口返回业务成功，等待查询结果 | 用户已提交账号，等待甲方审核 |
| 已加白 | 查询接口返回账号审核状态 1 | 管理员点击“报白通过” |
| 未通过 | 查询接口返回账号审核状态 2 | 管理员点击“报白未通过” |
| 提交失败 | 提交阶段失败，未确认成功提交甲方 | 新建人工记录不自动产生此状态；可保留转人工前已有的提交失败事实 |

提交失败时，数据库保存独立状态“提交失败”，管理端可见该状态和错误原因；用户端显示“审核中”，不展示提交失败标识或原因。该展示不表示甲方已经接收，不写入成功提交时间，也不安排查询任务。查询失败的真实状态仍为“审核中”，错误原因附加展示，不新增“查询失败”状态。人工记录允许从“待提交”直接进入“已加白”或“未通过”。

管理端账号报白页面增加导出，用于运营整理账号并同步线上表。线上表由运营手动维护；本方案不包含在线表格连接器、定时同步、表格导入或自动回写。

全部业务表格导出统一使用真正的 `.xlsx`：本次新增账号报白 Excel 导出，并将现有推广订单 CSV 导出一并改为 Excel。现有导出端点、下载文件名、按钮文案和调用方同步调整；不提供 CSV/XLSX 双格式选择。

甲方关于 TikTok 可直接推广的说明，不等于所有新建账号自动变成“已加白”。本次五个状态表示报备处理进度与结果，不新增以“已加白”为条件的推广链接生成限制。发布时的付费集范围、`#goodshort` 和站内引流链接由运营遵守，本次不增加发布系统。

## 2. 当前实现与变更点

以本次核对的 `7ce437c` 工作区为依据：

- 接入配置尚无按媒体选择报白方式的字段；原接入级 `filing_mode` 已由 `V4` 删除。
- `MediaAccountServiceImpl.create()` 当前对支持媒体创建 API 报白记录，初始为 `PENDING + SUBMIT`，事务提交后同步执行 `afterCommit -> submitNow()`；它不是独立异步队列。
- `GoodShortAdapter` 调用 `/creek/open/filing/report`，只有外层 `status=0 && success=true` 才算提交成功。
- 成功后 `completeSubmit()` 写入成功提交时间并安排查询；查询外层成功后，使用 `data.status` 的 0/1/2 判断审核结果。
- Worker 只扫描 `QUERY`；首次查询默认延迟 1 分钟，正常审核中每 5 分钟继续查询，Scheduler 每 30 秒扫描到期记录。
- 当前数据库 `PENDING/APPROVED/FAILED` 混合了业务状态与技术失败；两端还会根据成功提交时间和错误派生显示标签。
- 管理端账号报白目前没有导出接口；当前明确存在的业务 CSV 导出是管理端推广订单 `/api/admin/promotion/orders/export.csv`。
- 现有 `MediaAccountAdminServiceImpl.delete()` 通过 `cannotDelete()` 限制报白状态与任务动作，前端通过 `canDeleteAccount()` 隐藏部分删除按钮；本方案取消这些准入判断，保留权限、存在性与事务一致性校验。

本文实施后将替代 [2026-09-08 账号报白设计](2026-09-08-media-account-filing-final-design.md) 中 API-only、三种存储状态、错误状态处理及按状态限制删除的部分。实施完成前，旧实现仍是运行现状，不提前修改 current docs 为已实现。

## 3. GoodShort 接入配置

在现有接入编辑表单增加“API 自动报白媒体”：

```text
API 自动报白媒体
☑ Facebook   ☐ TikTok   ☐ YouTube   ☐ Instagram

勾选的媒体通过 GoodShort API 自动报白；未勾选的媒体由运营人工同步并更新结果。
```

- 新配置建议默认仅勾选 Facebook。其他复选框保留配置能力，运营应按甲方实际支持范围设置。
- 空集合表示全部人工报白；不能把未勾选解释为“不支持该媒体”或禁止创建账号。
- 此字段仅影响账号报白，不停用 GoodShort 的目录、剧集、订单、推广链接等 API，也不免除接入凭据配置要求。
- 沿用现有权限：超级管理员维护接入；普通管理员不能修改该配置。
- 请求字段建议为 `apiFilingMediaTypes: MediaType[]`，随现有 `PUT /api/admin/drama/providers/{providerId}/connection` 保存，并在现有接入响应中回显。
- 新建接入必须显式提交集合，允许 `[]`；更新时缺省字段保留原值，避免其他接入资料更新误清空配置。前端每次保存均显式携带当前集合。
- 后端拒绝未知媒体和重复媒体；只接受当前支持的四种媒体枚举。
- 复选框保存时同步切换该接入下对应媒体的已有报白记录，具体状态与动作按第 8 节处理；保存界面明确说明会影响已有记录，不只影响后续新增账号。

### 保存方式建议

在 `short_drama_connection` 增加 `api_filing_media_types`，以 JSON 数组文本保存，API 使用类型化数组。当前只涉及四个枚举且无独立配置生命周期，单字段足以表达复选框。

独立媒体配置关系表也可表达此需求，但会新增表和 Mapper；四个布尔列则把媒体类型固定进多个 schema 字段。本方案推荐单数组字段，不恢复接入级 API/MANUAL 总开关。

## 4. 报白记录与统一状态

每条 `provider_media_filing` 保存自己的 `filing_method = API | MANUAL`，创建时根据接入配置决定，配置切换时按第 8 节显式更新记录与任务。列表读取记录的实际方式，不能根据最新复选框临时推断。建议记录最近方式切换的管理员和时间，和人工审核操作分开，不把切换本身当成审核通过。

建议统一 `status` 枚举：

| 存储/API 枚举 | 中文 |
| --- | --- |
| NOT_SUBMITTED | 待提交 |
| PENDING | 审核中 |
| APPROVED | 已加白 |
| REJECTED | 未通过 |
| SUBMIT_FAILED | 提交失败 |

保留 `next_action`、`next_action_at`、错误、重试计数、任务版本和租约字段表达执行情况，不新增独立任务框架。使用 `SUBMIT_FAILED` 明确表达提交失败，`REJECTED` 表达审核未通过，不再沿用含义混合的 `FAILED`。查询技术错误保留 PENDING 并附错误信息。

- `last_submitted_at`：API 明确成功提交时间，或管理员核实不确定 API 提交并确认甲方已经收到的时间。新建人工记录进入审核中以及人工直接给出终态时均不虚构提交时间。
- 不新增 `api_submitted_at`。沿用 `submitted_data_version` 作为“report 曾明确返回业务成功”的证据：`completeSubmit()` 成功时写入当次 `task_data_version`，方式切换不清除。`submitted_data_version` 为空不等于请求一定未到甲方，还必须结合提交尝试和错误证据判断。
- 增加 `last_submit_attempt_at`，在真正调用 report 前通过已提交的短事务写入；明确开始一次获准重试前清空旧尝试值，再由新任务写入。report 已开始但未取得明确结果时写 `SUBMIT_FAILED + SUBMIT_OUTCOME_UNKNOWN`，用于后台人工核实，不能据此自动重报。
- `last_queried_at`：最近成功取得有效甲方查询结果的时间，仅 API 使用；它不是最后一次失败尝试的时间。
- `remote_status`、`filing_time`、`operate_time`：只保存甲方接口实际返回的状态与时间，人工操作不伪造这些字段。
- 新增 `manual_updated_by`、`manual_updated_at`，记录最近人工操作管理员与服务器时间。管理员身份从登录上下文取得；人工通过或未通过不要求填写原因，也不新增必填备注字段。
- 保留 `last_error_code/message` 作为技术错误。人工业务未通过不是技术异常，不写入技术错误字段。
- `task_data_version` 是每条报白任务的单调递增执行版本：新记录从 1 开始，方式切换、人工状态接续、失败重试和重新安排动作时均基于当前值加 1；不得用媒体账号的 `data_version` 覆盖或把版本重置为旧值。所有领取、完成、失败回写和人工核实均校验当次版本与租约。

本阶段建议只记录最近一次人工操作，不增加审批流或完整历史表。管理端状态标签直接使用真实 `status`；用户端使用面向用户的展示状态，提交失败时映射为 PENDING。展示映射只作用于用户响应，不能改写数据库实体或影响任务调度。

## 5. 两条处理链路

### 5.1 API 报白

```text
创建账号和 API 报白记录：待提交 + SUBMIT
  -> 单条新建在本地事务提交后尝试立即执行；未立即执行成功仍由 Worker 接续
  -> 批量方式切换只入队，由 Worker 分批调用 report
  -> 外层 status=0 且 success=true
  -> 审核中 + QUERY，保存成功提交时间
  -> 到期调用 query，先校验外层成功，再读取 data.status
       0 -> 审核中，继续查询
       1 -> 已加白，停止查询
       2 -> 未通过，停止查询
```

- report 的 HTTP 成功不能替代业务成功。report 的外层 `status=0` 不代表审核通过。
- report 明确失败或提交阶段本地处理失败：真实状态写为 SUBMIT_FAILED，记录错误并停止自动提交；用户端展示审核中，管理端展示提交失败。能够确认甲方未收到的可重试错误保留管理员重试入口；允许重试时先提升任务版本并转 NOT_SUBMITTED + SUBMIT，成功转 PENDING，再次失败转 SUBMIT_FAILED。
- report 调用已经开始但因超时、连接中断、进程退出等原因没有取得明确结果时，写 `SUBMIT_FAILED + SUBMIT_OUTCOME_UNKNOWN` 并停止自动提交和普通 retry。若进程未能完成错误回写，Worker 在租约过期后根据 `last_submit_attempt_at`、空的成功证据及原任务版本将其收敛到同一结果不确定状态，不直接再次调用 report。
- 结果不确定记录由管理员核实：确认甲方已收到时转 PENDING + QUERY，写人工确认时间和操作信息，但不伪造 `submitted_data_version`；确认甲方未收到时解除“不确定”限制，之后才允许管理员按正常 retry 重新入队。活动租约存在时不能执行该核实操作。
- query 临时失败：保持审核中，按现有退避重试；第 5 次连续临时失败停止查询，保留错误。恢复正常结果后清除错误和重试计数。
- query 非临时错误、空/未知审核结果：保持审核中，记录错误并停止查询，不能写成未通过。
- 已停止查询的记录在详情明确显示“查询已停止”和错误原因；本次不自动新增查询恢复入口。
- 提交、查询、领取任务和完成 SQL 均校验 `filing_method=API`；完成时继续核对任务版本、租约，防止旧任务覆盖新记录状态。
- 甲方 HTTP 调用在数据库事务之外，领取和结果写入使用能实际提交的短事务。必须验证从真实 Spring `afterCommit` 入口调用后，提交结果可被后续请求读取，不能只验证 mock 方法被调用。
- 现有 Worker 的到期扫描从仅处理 QUERY 改为同时处理 SUBMIT 和 QUERY，继续按批次、租约及现有限流逐条执行。单条新建账号保留 afterCommit 立即提交以缩短等待；配置切换产生的批量 SUBMIT 不逐条注册 afterCommit 回调，避免接入保存请求被批量远程调用阻塞。立即提交未抢到租约或应用在 afterCommit 前后退出时，未开始的 SUBMIT 仍可被 Worker 接续。
- 保留 report/query 独立限流与上海时区转换。

以上为新建 API 记录的主链。已有人工审核中记录转 API 时采用第 8 节的先查询策略，不重复 report；人工审核中状态不等于 API 提交成功证据。查询有效结果可以正常推进状态，查询空结果或错误不能自动触发 report。

### 5.2 人工报白

创建记录为 `MANUAL + PENDING + NONE`，没有下次 API 处理时间，不调用 report/query。用户提交时间不写入 `last_submitted_at`，该字段不用于伪造甲方实际接收时间。

| 当前状态 | 管理员操作 | 结果 |
| --- | --- | --- |
| 待提交、审核中、未通过 | 报白通过 | 已加白；记录管理员、操作时间 |
| 待提交、审核中、已加白 | 报白未通过 | 未通过；记录管理员、操作时间 |

存量 API 记录转为人工后，如保留 NOT_SUBMITTED 或 SUBMIT_FAILED，允许管理员直接标记已加白或未通过以继续处理。新建人工记录直接从审核中开始，不提供“标记已提交”或手动“提交失败”按钮；两种方式共用状态枚举，不要求产生所有状态。

人工“已加白/未通过”按启用/停用式结果切换处理，不作为不可修改终态：已加白记录可直接点“报白未通过”切为未通过，未通过记录可直接点“报白通过”切为已加白。不新增“纠错”流程、状态下拉框或原因填写步骤，也不要求先退回审核中。该操作只适用于 MANUAL 记录，API 记录仍以甲方查询结果为准。

沿用媒体账号管理权限，普通管理员和超级管理员均可处理人工记录；推广用户只读。后端在短事务中校验记录归属、方式和允许的状态转换，使用带当前状态条件的更新。并发的通过/未通过只能一个成功，另一方收到状态已变更提示并刷新。

## 6. 管理端、用户端与接口

### 管理端

- 列表增加“报白方式：API / 人工”，报白状态筛选提供待提交、审核中、已加白、未通过、提交失败五项；建议增加报白方式筛选供运营导出人工账号。
- 人工待提交或审核中记录显示“报白通过、报白未通过”；人工已加白显示“报白未通过”，人工未通过显示“报白通过”，操作方式沿用启用/停用式直接切换。转人工后保留提交失败的记录，按第 5.2 节提供处理操作；不提供“标记已提交”。
- API 记录由接口更新结果，不显示人工状态操作；技术提交重试按钮与后端允许条件一致。
- 提交失败记录直接显示独立“提交失败”状态，并展示错误原因和符合条件的重试操作；筛选与导出均识别 SUBMIT_FAILED，不归入待提交。
- 详情分清“报白状态”和“处理异常”。人工记录展示最近操作人和人工操作时间，不要求展示未通过原因，不显示虚假的甲方审核时间或下次查询时间。
- 导出不会改变报白状态；新建人工记录在用户提交时已经进入审核中。
- 每个账号详情均提供删除按钮，不依据报白状态、方式、报白记录数量或任务租约隐藏/禁用。沿用现有删除确认交互，说明删除的是本系统媒体账号和报白记录，甲方记录不会被同步删除；请求成功后关闭详情并刷新列表。

### 用户端

继续新增和查看账号，状态文案使用待提交、审核中、已加白、未通过，不提供人工操作或重试入口。

| 实际情况 | 用户端展示 | 管理端展示 |
| --- | --- | --- |
| 正常待提交，尚无提交错误 | 待提交 | 待提交 |
| 提交失败，未确认成功提交甲方 | 审核中，不提示提交错误 | 提交失败，可查看原因 |
| 成功提交后等待结果 | 审核中 | 审核中 |
| 甲方查询或人工操作给出未通过结果 | 未通过 | 未通过 |
| 甲方查询或人工操作给出通过结果 | 已加白 | 已加白 |

用户端列表、详情及创建后的重新查询统一应用上述映射。用户响应不返回提交失败错误码或原因，前端也不弹出提交失败通知；本地创建账号失败、参数错误等正常请求错误仍按现有规则提示。查询异常维持原方案的安全摘要提示，不与本次提交失败隐藏规则混淆。

建议后端在用户专用 VO 转换中将真实 `status=SUBMIT_FAILED` 映射为展示 `status=PENDING`，屏蔽该记录的提交错误字段；真实 `lastSubmittedAt` 仍为空，不伪造提交成功。该映射与报白方式无关，也适用于转人工后保留的提交失败。管理员重试会将真实状态转回 NOT_SUBMITTED 并清理错误，重试处理中恢复正常待提交展示，成功后或再次失败后按上表展示。本次不额外保存隐藏失败的历史展示状态。

### 管理端单条删除，不限报白状态（已确认）

普通管理员和超级管理员沿用现有媒体账号管理权限，每次只删除当前选中的一条媒体账号，删除请求只携带该账号内部 ID，不接受账号集合或按筛选条件删除。该账号没有报白记录、有多个平台报白记录、已成功提交、已加白、查询异常或存在运行中的任务，均不构成业务拒绝条件。用户端仍只读；媒体账号在存在期间继续保持不可编辑及平台/账号 ID 全局唯一。

删除的实现边界：

1. 保留按选中账号内部 ID 加锁及存在性检查，在同一短事务内先按 `media_account_id = 当前账号ID` 删除关联 `provider_media_filing`，再按 `id = 当前账号ID` 删除唯一一条 `promotion_media_account`；无报白记录时直接删除该账号，不报“状态不允许删除”。任一步失败均回滚。这里删除的关联报白记录仅属于这一条账号，不涉及其他媒体账号。
2. 不再调用 `cannotDelete()` 或返回因报白状态触发的删除拒绝。正常权限、记录不存在、数据库失败仍按实际结果处理；不能吞掉真实删除错误并提示成功。
3. 删除报白记录即移除本地待执行动作。Worker 已扫描但尚未领取的 ID 应领取失败或读取为空后退出；发请求前检查记录是否仍有效。已发出的 HTTP 可能继续在甲方处理，删除不等待租约结束，也不承诺取消远端请求。
4. report/query 完成、错误重试回写、人工更新和方式切换均不能重建已删除记录。旧任务结果以原报白内部 ID、版本、租约条件更新，发现记录已删除时丢弃结果并结束，不安排新任务；不能按相同外部账号 ID 回查并写入后来新建的账号。
5. 删除后列表、详情及导出不再返回该账号；释放本地全局唯一值，允许以后重新创建相同媒体平台和账号 ID，新记录使用新的内部 ID，并按创建时的配置与正常提交逻辑处理。旧任务不能污染新记录。
6. 此操作只删除本系统媒体账号及其全部报白记录，不删除推广用户、订单、佣金、推广链接或平台接入。甲方接口文档未提供撤销/删除报备能力，不声称本地删除会清除甲方审核结果；重新创建也不代表甲方已清除旧报备。

删除与方式切换使用同一套锁定顺序及条件更新保证一致性，但准入不同：方式切换可按第 8 节等待活动任务结束；删除不以活动任务为由拒绝。短事务正常锁等待不是新增状态限制，不在事务内等待甲方网络返回。

通用导出契约：

- 已核对的 CSV 消费者是管理端订单页面；实施时检查直接调用方与相关测试，协同替换旧路由和 CSV 序列化，不增加无消费者的兼容别名。

账号报白导出规则：

- 按当前业务筛选条件导出全部匹配记录，不只导出当前分页；不因当前页大小截断。

- 两处导出均按当前筛选条件导出全部匹配数据，不设置固定行数上限，也不能静默截断；不受管理端列表分页影响。本次不建设异步导出中心，后续只有在真实数据规模造成明确性能问题时再单独设计限制或异步方案。

## 8. 人工与 API 双向切换及存量迁移建议

### 8.1 切换入口与范围

已确认以 GoodShort 接入中的媒体复选框作为唯一切换入口：某媒体勾选变为 API，取消勾选变为人工，保存时覆盖该接入、该媒体已有记录，并作用于后续新账号。不额外增加逐账号覆盖配置，避免复选框含义与记录长期不一致。

方式变化不表示重新审核，更不表示审核通过。已有终态保留；未完成记录按下表接续处理。重复保存相同配置不重排任务、不清除错误、不重新提交。

### 8.2 人工转 API

| 当前真实状态 | 切换后的状态 | 后续动作 |
| --- | --- | --- |
| 待提交 | 待提交 | 无成功提交或未决提交证据时写 SUBMIT + next_action_at，由 Worker 分批 report；成功转审核中，失败转提交失败 |
| 审核中 | 审核中 | 已由运营确认提交，先调用 query 同步结果，不重新 report |
| 已加白 | 已加白 | 保留已有通过结果，不 report、不 query |
| 未通过 | 未通过 | 保留已有拒绝结果，不自动重新报白 |
| 提交失败 | 提交失败 | 保留失败及原因，按现有技术重试规则由管理员发起 retry；不利用方式切换绕过限制 |

人工审核中可能来自线上表同步，甲方 API 未必能够查询到。方案采用前述推荐：先查询，不统一重新提交，也不将“人工同步记录一定能被 API 查询”写成已知事实。有效 `data.status=0/1/2` 分别对应审核中、已加白、未通过；空数据、未知状态或查询请求被拒绝时，保持审核中并记录查询异常、停止查询，后台提示管理员核实；临时网络错误沿用最多 5 次重试。查询请求失败与有效审核结果 `data.status=2` 必须区分。无查询结果不能推导为账号未提交，更不能自动重报，运营可切回人工继续处理。只有甲方另行确认人工记录需要 API 重提且重复提交安全后，才另行设计重提规则。

待提交与成功提交证据并存，或待提交存在尚未处理的 `SUBMIT_OUTCOME_UNKNOWN`，都属于需要核实的数据，不能直接重复 report。已加白、未通过的终态来源可能是人工，切成 API 后仍保留人工结果来源，不伪造 `remote_status` 或甲方审核时间。

### 8.3 API 转人工

| 当前真实状态 | 切换后的状态 | 后续动作 |
| --- | --- | --- |
| 待提交 | 待提交 | 停止待执行 report，运营直接处理通过或未通过 |
| 审核中 | 审核中 | 停止 query，保留真实提交和查询事实，由运营接续审核结果 |
| 已加白 | 已加白 | 保留结果，不重新人工审核 |
| 未通过 | 未通过 | 保留结果，不自动重置为待提交 |
| 提交失败 | 提交失败 | 保留失败及原因，开放人工通过、未通过操作 |

全部转人工记录写为 `next_action=NONE`、清除下次执行时间，失效旧租约。仅在人工操作成功落库后清除已处理的提交错误；查询错误可在切换时结束其“当前异常”含义，并保留切换前核对记录。切换不删除账号、不创建重复报白记录、不释放账号唯一性。

### 8.4 在途任务、重复切换与事务

- 方式与任务动作在同一数据库事务中更新，按 `task_data_version = task_data_version + 1` 提升任务版本并失效原租约；旧 report/query 的结果及异常回写均须检查领取时的方式、版本、租约，不能覆盖新的方式或人工结果。失败重试、人工接续和重新安排动作使用同一递增规则，不能复用当前把任务版本写回媒体账号 `data_version` 的 `reschedule()` 行为。
- 方式切换使用专用条件 UPDATE，只修改方式、状态、动作、下次时间、递增后的任务版本、租约及规则明确要求处理的错误/重试字段；不得复用会清空 `submitted_data_version`、甲方结果、提交/查询时间等真实证据的现有 `reschedule()`。
- API 调用发出前再次校验任务有效性，减少已切换后仍发出旧请求的机会。请求一旦发出，不能保证撤回；尤其 report 超时或恰逢切换时，甲方可能已经接收而本地尚无成功时间，不能声称“取消勾选就取消甲方提报”。
- 存在活动租约时拒绝本次方式切换、保持原配置不变，提示正在处理后再试；租约过期但 `last_submit_attempt_at` 表明曾发起 report、且没有明确成功/失败结果的记录，先收敛为 `SUBMIT_OUTCOME_UNKNOWN` 并由人工核对甲方接收情况，不自动再次 report。不能只根据成功时间为空断定未发送。
- 接入保存、账号创建和任务领取应使用一致的锁定顺序与条件校验：保存不能漏掉并发新建的旧方式记录，任务领取不能越过切换事务；数据库事务内不执行甲方 HTTP。
- 新建单条账号的 report 可在事务提交后立即尝试；切换产生的批量 report 只写入任务，由扩展后的现有 Worker 分批消费 SUBMIT 和 QUERY。切换后再次切回，依据当前真实状态、`submitted_data_version`、`last_submitted_at`、`last_submit_attempt_at` 和错误证据处理，不依据最初创建方式回放历史任务。
- 配置更新仅修改当前接入中勾选发生变化的媒体；不影响其他平台、媒体或无关 API 功能。记录更新失败应回滚本次配置与方式变更，不返回部分成功。

上述方案复用现有任务服务与 Mapper，不建立切换调度平台。双向切换与五个状态是两条独立维度，不增加“切换中”业务状态。

### 本次上线的已有非 Facebook 记录

为落实甲方“其他平台人工同步”，本次上线计划在发布窗口对既有 GoodShort 非 Facebook 记录按上面的 API 转人工规则完成首次初始化；切换范围仍需按生产记录核对：

1. 暂停应用报白执行并等待在途调用结束，备份接入配置与报白记录；核对待提交、审核中、终态和异常记录数量。
2. GoodShort 接入配置初始 API 媒体为 Facebook；记录按媒体设置 API 或 MANUAL。
3. 非 Facebook 人工记录全部停止 API 动作，清理租约与下次任务时间，提升任务版本；保留真实提交时间及已获取的甲方结果。
4. 不依据聊天回复批量把所有账号标成已加白；对明确获甲方确认的账号由管理员按人工流程处理。

旧状态建议按以下优先级回填；上线前先查出互相矛盾的记录并逐条核实，不强行猜测：

| 旧证据 | 新状态 |
| --- | --- |
| `remote_status=1` 或已有可靠 APPROVED 结果 | APPROVED |
| `remote_status=2` | REJECTED |
| 没有终态结果，`last_submitted_at` 非空 | PENDING，包括查询技术失败 |
| 没有终态结果，`last_submitted_at` 为空，存在提交错误 | SUBMIT_FAILED，包括 report 技术失败或请求拒绝 |
| 没有终态结果，`last_submitted_at` 为空，且没有提交错误 | NOT_SUBMITTED |

旧 `FAILED` 不能统一转换为未通过，也不能统一转换为提交失败，必须按提交时间、甲方结果与错误区分。切到人工的记录停止任务、清零重试计数；提交失败状态及其原因保留，后续人工操作成功落库时清除旧技术错误。已有审核中保留实际成功提交事实，可清除已停止 API 查询的技术错误，旧值由发布备份保留；不重新伪造人工提交。

存量 `submitted_data_version` 原样保留，非空值继续作为已有 API report 明确成功的证据；新增的 `last_submit_attempt_at` 不根据旧错误或旧提交时间猜测回填。发布前发现“可能发出请求但无明确结果”的旧记录时逐条核实，不通过迁移脚本自动重报或伪造成明确成功。

schema 变更只新增更高版本 Flyway 迁移，不修改已执行的 `V1..V8`；实际版本号在实施时按最新迁移链分配。同时更新开发重建脚本和受影响测试 schema，保持最终结构一致。生产迁移由独立 Flyway 发布步骤执行，应用启动不迁移。

新枚举、方式字段和前端共同发布，避免旧 Worker 按旧状态写回。回滚必须停应用并处理发布后新增人工记录，不能直接运行旧程序或无条件覆盖整个库；旧版本恢复需要按已核对的备份恢复本次相关数据，发布后新增记录应先导出核对。

## 9. 分阶段实施与验收

以下是实施顺序，尚未执行：

1. 落实已确认的双向切换规则、新字段、统一枚举与迁移映射；发布前核对首次生产存量切换范围及异常数据。
2. 实现接入媒体配置、记录方式持久化、双向切换、五状态处理及 SUBMIT/QUERY 后台消费；完成 API 与人工入口隔离。
3. 实现人工状态更新、两端展示与筛选，保留技术重试条件；移除管理端账号删除状态限制，处理删除与在途任务的并发。
4. 新增账号报白 XLSX 导出，将现有订单 CSV 导出及其调用方同步转换为 XLSX，验证长 ID、金额口径与筛选范围。
5. 运行验证、执行发布前存量核对；实施完成后更新 current docs 并归档被替代方案。

验收场景：

- 勾选 Facebook 后新 Facebook 记录走 API；未勾选媒体创建 `MANUAL + PENDING + NONE` 人工记录，report/query 均无调用；空集合为全部人工。
- 接入媒体配置切换按两张状态表同步更新对应已有记录；未变化媒体及其他平台不受影响；非法媒体、重复媒体和无权限写配置被拒绝。
- 人工待提交转 API 只批量写入到期 SUBMIT，不在配置保存请求中逐条调用 report；Worker 按批次和限流提交。人工审核中先 query，查询无记录不自动 report；已加白、未通过双向切换均保留终态且不重报；提交失败转 API 不绕过管理员 retry 条件。
- API 转人工后不再领取新任务，人工可以接续处理；活动租约阻止切换，超时在途 report 不能盲目再次提交；旧任务结果及错误回写不能覆盖切换后的状态。
- 反复切换、重复保存、并发创建与任务领取不产生重复报白记录或重复安排同一提交；接入配置和受影响记录更新失败时整体回滚。任务版本在切换、retry 和人工接续后严格递增，不能回退为账号版本或复用旧版本。
- 正常等待或执行 report 时为待提交，提交失败写为 SUBMIT_FAILED，成功后真实状态才转为审核中；query 0/1/2 分别映射审核中/已加白/未通过。
- report 超时、连接中断和模拟“请求发出后进程退出”均不得自动重复提交；有错误回写时直接形成 `SUBMIT_OUTCOME_UNKNOWN`，无错误回写时在租约过期后由 Worker 收敛为同一状态。管理员确认已收到后进入审核中并查询，确认未收到后才允许 retry；两种操作均不能伪造 API 明确成功证据。
- 提交和查询技术异常不变成未通过；第 5 次连续查询技术错误停止任务但保持审核中；成功查询清理错误。
- 新建人工记录直接进入审核中；人工从存量待提交或审核中直接设为已加白/未通过均可，人工已加白与未通过可像启用/停用一样直接互相切换，不要求原因或先退回审核中。API 记录不能被人工修改；并发状态更新不能互相覆盖。
- 管理端标签、筛选与导出均使用真实状态；用户端列表、详情使用一致的展示映射；人工直接通过时即使提交时间为空也显示已加白。
- report 提交失败时，数据库为 SUBMIT_FAILED；用户显示审核中且响应、页面无提交失败标识或原因；管理端列表、详情、筛选及导出均识别提交失败。数据库无成功提交时间、不创建 QUERY，管理员原有重试条件不受用户展示影响。
- 获准重试时 SUBMIT_FAILED 转 NOT_SUBMITTED，成功转 PENDING，再次失败回 SUBMIT_FAILED；迁移后的人工提交失败记录保留原因，用户端仍映射为审核中，按人工流程处理后展示实际结果。
- 正常尚未提交仍显示待提交；甲方查询明确拒绝仍显示未通过，不能被提交失败映射覆盖；本地创建失败仍提示请求错误。管理端详情不能受复用用户 VO 的展示映射影响。
- API 技术重试条件不被统一状态或切换绕过；管理员可删除五种状态下的 API/人工账号，无报白记录、多平台报白记录和运行中的任务均不阻止删除；普通推广用户仍不能调用删除接口。
- 选中账号 A 删除时，只删除 A 及其关联报白记录，账号 B 及 B 的报白记录、任务保持不变；不因当前筛选或同一推广用户扩大删除范围。失败时整体回滚；权限和不存在错误正常返回；前端各状态均有单条删除入口，成功后刷新列表，导出不再包含已删除账号。
- 删除与任务领取、report/query 成功或失败回写、人工状态更新、方式切换并发时不产生孤立或复活记录；旧任务不得写入删除后新建的同外部账号 ID 记录；其他账号、用户、订单、佣金及推广链接不受影响。
- 真实 Spring 事务入口下提交结果可持久化；人工方式不可被 Worker 领取，旧版本/旧租约结果不能写回。
- 导出跨分页完整并覆盖当前筛选条件下的全部匹配数据，不设置固定行数上限或静默截断；19 位账号 ID、前导零、中文、引号、换行和公式样式文本保持为正确数据。
- 账号报白导出表头严格为“创建时间、昵称、姓名、电话、微信号、媒体平台、账号 ID、账号名称、账号链接、报备状态、短剧平台”，顺序一致且恰好 11 列；创建时间来自媒体账号，联系方式来自所属用户，短剧平台来自当前行报白记录，空联系方式留空，提交失败导出真实状态。
- 两处文件均能作为真实 XLSX 工作簿解析，Excel 打开无格式不匹配提示；响应类型、附件扩展名与前端按钮一致，订单原有列集合、筛选和金额/佣金结果保持一致。
- 现有订单 CSV 路由、序列化及前端调用同步替换，受影响测试和当前文档更新为 XLSX；历史归档不做格式替换。
- 迁移区分“技术失败”与“甲方拒绝”，保持已知结果；开发重建和完整迁移链最终结构一致。

实施后的 canonical Gate：后端 `./mvnw.cmd verify`，管理端和用户端各自 `pnpm check`，根目录 `git diff --check`；按 [测试规范](../../development/testing.md) 记录退出码、测试数量和环境限制。MySQL 缺真实环境记 SKIP，真实执行失败记 FAIL。现有 GoodShort Real Smoke 针对免费内容，不能替代账号 report/query 的真实验收；报白真实验证需使用已授权的账号与环境，不批量重报生产账号。

本次仅编写设计文档，以文档范围、链接和 diff 检查验收，不将应用 Gate 的历史结果当成本次验证。
