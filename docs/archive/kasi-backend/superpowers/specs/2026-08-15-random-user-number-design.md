# 12 位随机用户编号设计

## 目标

将推广用户对外展示的 `user_no` 从可推断用户数量的 `KS + 自增 ID` 改为固定 12 位随机数字字符串。系统内部继续使用自增 `id` 作为主键和关联键，普通推广用户的业务响应对象不再直接展示该内部 `id`。

## 核心决策

- 不使用雪花算法。项目长期为单实例、单数据库且用户规模不超过约 3000 人，不需要分布式全局主键；雪花 ID 还会暴露生成时间和先后顺序。
- `promotion_user.id` 保持 `BIGINT UNSIGNED AUTO_INCREMENT`，继续用于 JWT `sub`、Redis 会话、密码重置、管理操作和未来业务表关联。
- `promotion_user.user_no` 使用 `SecureRandom` 生成，格式为首位非零的 12 位纯数字字符串，例如 `583104726918`。
- `user_no` 是公开展示和搜索编号，不参与登录、鉴权或数据库表关联，也不作为安全凭据。
- 本次采用普通展示层隐藏：登录和本人信息 JSON 不返回 `id`，但签名 JWT 的 `sub` 仍保存内部 `id`。JWT 未加密，技术用户可以解码该值；本功能不将用户规模隐藏定义为安全边界。

## 数据库契约

- 将生产迁移和 H2 测试 schema 中的 `user_no` 改为 `CHAR(12) NOT NULL`。
- 保留 `user_no` 唯一索引，数据库是唯一性的最终保障。
- Java Entity、VO 和 JSON 中的 `userNo` 继续使用 `String`，防止调用方将业务编号误当成可计算数值。
- 项目仍处于可重建数据库阶段，因此直接修改 `V1__kasi_promotion.sql`；执行过旧 V1 的开发数据库必须删除并重建。

## 编号生成组件

新增职责单一的用户编号生成组件，使用单个长期复用的 `SecureRandom` 实例。每次生成范围为 `100000000000` 至 `999999999999` 的十进制字符串，不添加 `KS`、时间戳或其他前缀。

生成组件只负责产生候选编号，不查询数据库。Service 负责创建用户和处理唯一约束，Mapper 仍只负责单表持久化。

## 创建流程

用户自助注册和管理员新增推广用户共用同一个编号生成组件：

1. 完成 DTO 校验、联系方式规范化、验证码及联系方式唯一性等现有业务校验。
2. 在插入前生成 12 位 `userNo` 并写入 `PromotionUser`。
3. 自助注册的默认昵称在插入前设置为 `用户 + userNo`；管理员新增继续使用请求中的昵称。
4. 执行一次 `INSERT` 并取得自增 `id`。
5. 删除 `TMP-*` 临时编号、UUID 依赖、`updateUserNo` Mapper 方法及插入后的第二次 `UPDATE`。

## 冲突与失败处理

- 每次创建最多尝试 3 个随机编号。
- `user_no` 唯一键冲突时生成新编号并重试插入。
- 捕获唯一键冲突后先按规范化后的手机号和邮箱回查：存在联系方式冲突时继续返回现有 `USER_MOBILE_DUPLICATE` 或 `USER_EMAIL_DUPLICATE`；联系方式均未冲突时才将异常视为 `user_no` 碰撞并重试。
- 连续 3 次编号冲突时抛出内部状态异常，整个创建事务回滚，不保留半成品用户。
- 非唯一键数据库错误不重试，沿用全局异常处理。

## API 边界

- `POST /api/user/auth/login` 的用户信息不再返回内部 `id`，保留 `userNo` 和现有资料字段。
- `GET /api/user/auth/me` 不再返回内部 `id`，保留 `userNo` 和现有资料字段。
- `/api/user/management/**` 面向管理员，列表、详情和写操作继续返回或接收内部 `id`，避免改变现有管理路径。
- JWT `sub`、Redis Key 和密码重置 Token 的内部身份仍使用 `id`，不改为 `userNo`；登录响应中的 Token 因此仍可被客户端解码得到内部 `id`。

## 测试

- 为编号生成组件添加单元测试，验证固定 12 位、只含数字、首位非零，并使用可控随机源使测试可复现。
- 为用户自助注册和管理员新增添加测试，验证插入时已持有最终编号、不再出现 `TMP-*`、不执行二次编号更新，默认昵称与最终编号一致。
- 添加可控碰撞测试，验证 `user_no` 冲突会重试、手机号或邮箱冲突不会被重试掩盖、3 次碰撞后事务失败。
- 更新用户登录、本人信息、管理查询与管理变更测试：普通用户响应不包含 `id`，管理响应保留 `id`，所有新生成编号符合 12 位数字格式。
- 更新测试固定数据为 12 位数字编号，并验证生产 V1 与 H2 schema 的字段长度和唯一约束。
- 完成后在 Java 25 环境运行定向测试、完整测试、跳过测试编译检查和 `git diff --check`。

## 不在范围内

- 不修改管理员账号编号体系。
- 不改变登录账号、JWT 生命周期、Redis 会话模型、密码重置流程或权限规则。
- 不加密 JWT，也不调整 JWT `sub` 或认证上下文中的内部 `id`；严格防止技术用户推断内部编号不在本次范围内。
- 不新增按 `userNo` 登录、鉴权或关联业务表的能力。
- 不迁移或保留开发数据库中的旧 `KS` 编号；开发数据库按现有约定重建。
