# 推广平台账号报白方式配置设计

日期：2026-08-19

## 1. 目标

在“推广管理”下增加“账号配置”页面，让管理员按平台选择账号报白方式。每个平台独立配置，首期支持 GoodShort，后续新增短剧平台或其他推广平台时沿用同一结构。

本配置只决定账号报白走 API 自动流程还是人工流程，不负责维护平台 URL、PID、KEY 等接入凭据。平台接入凭据继续放在“系统配置 / 短剧 API 配置”。

## 2. 菜单与职责

```text
推广管理
├── 账号报白       处理具体媒体账号的报白状态
└── 账号配置       配置各推广平台的报白方式

系统配置
└── 短剧 API 配置  维护 URL、PID、KEY 和平台连接状态
```

职责边界：

- “账号配置”是推广业务配置，按平台保存报白方式。
- “账号报白”是具体账号的操作页面。
- “短剧 API 配置”是平台连接配置，不能与报白方式混在同一表单。

## 3. 页面交互

页面采用纵向表单，不使用开关和卡片堆叠。每个平台显示一组单选项：

```text
GoodShort       ○ API 自动报白    ● 人工报白
                提交媒体账号后，系统是否自动调用该平台的报白接口
```

约束：

- 同一平台只能选择一种方式。
- 不同平台之间互不影响。
- 首期 GoodShort 默认使用 API 自动报白，管理员可以改为人工报白。
- 保存按钮统一提交本页修改，保存成功后提示结果并刷新当前配置。
- 页面不提供“失败原因”输入框。

## 4. 报白流程

### 4.1 API 自动报白

1. 用户提交媒体账号。
2. 系统创建平台报白记录并进入“审核中”。
3. 后台任务调用平台 API 提交并查询审核状态。
4. 平台返回通过时改为“已加白”，明确失败时改为“已失败”。

### 4.2 人工报白

1. 用户提交媒体账号。
2. 系统创建平台报白记录，状态为“审核中”，但不创建或领取第三方 API 报白任务。
3. 管理员在“账号报白”页面打开该账号详情。
4. 管理员直接选择“已加白”或“已失败”。
5. “已失败”只更新状态，不要求填写失败原因；系统自动记录操作管理员和操作时间。

切换报白方式只影响之后的新提交。历史账号和历史报白记录不被自动重置。切换到人工报白时，尚未执行的 API 报白任务不再继续执行，但历史任务记录保留。

## 5. 状态与数据规则

对外业务状态仍只有三种：

| 状态 | 含义 |
| --- | --- |
| 审核中 | 已提交或等待人工处理，尚未得到最终结果 |
| 已加白 | 管理员或平台确认报白通过 |
| 已失败 | 管理员或平台确认报白失败 |

报白方式建议保存在平台接入配置边界上（当前为 `short_drama_connection`），因为实际 API 报白使用的就是该接入账号。即使当前每个平台只有一套接入账号，后续增加多套账号时也不需要重新设计业务模型。

建议字段：

- `filing_mode`：`API` 或 `MANUAL`。
- 默认值：`API`。

人工失败不新增业务失败原因字段，也不要求写入说明。现有自动任务的技术错误字段仅用于后台排查，不出现在人工操作表单中。

## 6. 管理员接口边界

接口名称以现有 `/api/admin/drama/providers` 平台接口为基础扩展：

- 查询平台列表时返回当前 `filingMode`。
- 超级管理员修改指定平台的 `filingMode`。
- 管理员在账号报白接口中将单个平台报白记录更新为“已加白”或“已失败”。

权限沿用现有规则：平台配置修改仅超级管理员可执行；账号报白状态处理由有权限的管理员执行。状态更新必须校验当前状态和平台配置，禁止重复处理已完成的记录。

## 7. 测试与验收

- 页面每个平台只存在一个单选组，API 和人工选项互斥。
- GoodShort 修改为人工报白后，新提交账号不创建 API 报白任务。
- 人工报白可以由管理员分别改为“已加白”和“已失败”。
- “已失败”操作不要求失败原因，接口请求中也没有该字段。
- API 自动报白流程保持现有提交、查询和重试行为。
- 修改一个平台的报白方式不会影响其他平台。
- 普通管理员不能修改平台报白方式；有权限的管理员可以处理账号报白状态。
- 前后端测试覆盖配置查询、配置修改、人工状态更新、权限和非法状态转换。
